# LDD 0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Build a maintainable Windows 10/11 LDD 0.2.0 desktop client that runs DeepSeek Harness 0.1.1-rc.2 from a replaceable runtime, supports verified online/offline kernel updates and rollback, enables DeepSeek vision with 20/64 MiB source-image modes, and analyzes local videos through a bundled FFmpeg DSH plugin.

**Architecture:** A sandboxed Electron shell supervises a standalone Node 24 Harness process. Immutable runtime versions live below LocalAppData while profiles, plugins, sessions, settings, and credentials remain below the LDD-owned DSH_HOME. Runtime installation is a staged transaction with manifest verification, two-phase health checks, atomic pointer switching, and last-known-good rollback. Video analysis remains an out-of-tree dsh.bundle that extracts frames locally, creates timestamped contact sheets, calls an image-capable LLM, and records reconstructable analysis inputs.

**Tech Stack:** Electron, TypeScript 6, React 19, Vitest, pnpm 11.7, Zod, execa, yauzl, semver, Vite, electron-builder/NSIS, Node.js 24 x64, FFmpeg/ffprobe, DeepSeek Harness 0.1.1-rc.2.

**Spec:** docs/superpowers/specs/2026-08-22-ldd-runtime-multimodal-update-design.md

## Global Constraints

- Target Windows 10/11 x64; no installed Node, pnpm, Python, Harness, or FFmpeg may be required.
- Keep Harness Web UI; do not build a separate chat client.
- Build the first runtime from the supplied official 0.1.1-rc.2 source snapshot with SHA-256 47fb7e386c0bd86a6c4341321b8f2915cd6f490a687f8deaf78714e369e4c91d.
- Reconstruct only the LDD Electron shell from the old EXE; do not reverse engineer Harness packages when source exists.
- Run Harness with standalone Node 24, never ELECTRON_RUN_AS_NODE.
- Keep renderer contextIsolation=true, sandbox=true, nodeIntegration=false.
- Bind Harness only to 127.0.0.1 and verify process identity before attaching to a port.
- Never overwrite the active runtime, previous runtime, fallback runtime, real profile, or user data during candidate validation.
- Default image admission is 20 MiB; large mode is 64 MiB; both retain the upstream pixel, count, aggregate, and normalization bounds.
- Third-party plugins require explicit user confirmation and are not installed by runtime updates.
- Use test-driven development for every behavioral change and run the named red test before writing its production implementation.
- Preserve all user-owned and unrelated files; destructive cleanup is limited to transaction-owned staging and private temporary media paths.
